# 아키텍처 컨벤션 — v1.1

## 프로젝트 결정 사항
- 클래스와 컴포넌트는 코드 길이나 메서드 개수가 아니라 **의미 있는 책임**에 따라 분리한다.
- 작고 응집도 높은 기능은 함께 유지하고, 책임·의존성·변경 이유가 달라질 때 분리한다.
- 추상적인 설계 원칙을 만족시키기 위해서만 인터페이스, 매니저, 이벤트, 추가 계층을 만들지 않는다.

## 책임 분리
- 거대한 단일 MonoBehaviour보다 응집도 높은 컴포넌트를 우선한다.
- 복잡성이 정당화될 때 입력 수집, 게임 규칙 판단, 이동/물리, UI 표현을 분리한다.
- 의존성을 명확히 하고 상태 소유자를 분명히 한다.
- 구체적인 필요가 없다면 매니저 클래스나 추상화 계층을 만들지 않는다.

## 이벤트
- 결합도를 낮출 필요가 있다면 C# 이벤트 또는 프로젝트에서 이미 사용하는 메시징 패턴을 활용한다.
- 이벤트의 소유자를 정하고 구독/해제를 대칭적으로 관리한다.
- 직접 호출이 더 명확한 간단한 관계에서는 불필요하게 이벤트를 사용하지 않는다.
- 기존 이벤트 시그니처를 변경하기 전에 구독자를 확인한다.

## 매니저와 싱글톤
- 공유 인스턴스가 실제로 필요한 경우에만 싱글톤을 허용한다.
- 모든 시스템을 기본적으로 싱글톤으로 만들지 않는다.
- 싱글톤 구현 시 중복 인스턴스와 생명주기 처리를 명시한다.

## 데이터와 설정
- 공유 가능한 에디터 설정 데이터에 적합하면 ScriptableObject를 사용한다. 모든 데이터 클래스를 대체하지 않는다.
- enum은 안정적이고 유한한 상태 또는 식별자에 사용한다. 관련 없는 시스템을 하나의 enum으로 결합하지 않는다.
- 깊은 상속 계층보다 컴포지션을 우선한다.

## 변경과 호환성
- 기존 프리팹/씬 참조와 직렬화 데이터를 보존한다.
- 리팩터링 전 영향받는 호출 코드와 직렬화 의존성을 확인한다.
- 명확한 이유 없이 디렉터리 구조나 네임스페이스를 변경하지 않는다.
- 승인 없이 서드파티 프레임워크를 추가하지 않는다.
